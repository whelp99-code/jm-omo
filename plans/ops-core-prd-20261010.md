## 1. 문제

## 3. 핵심 흐름 (첫 시나리오)
백업 실패 알림 수신 → 중복 이벤트 제거(D8) → 사건 묶기 → 담당 배정 → 사람이 장비 조치, 플랫폼에 조치 기록(장비 *변경* 작업이면 승인 번호 필수, 조사·기록만인 조치는 승인 번호 강제 안 함) → 다음 백업 결과 재조회로 검증 → 종료(D10) → 고객별 보고에 반영.

## 4. 데이터 원칙 (시험: T-AUDIT-1, T-SEC-1)
모든 사실에 출처 시스템·원본 ID·관측 시각·확인 상태. 관측 시각 없음 = 미확인. 고객별 격리, 감사 기록. 접속 비밀 값은 금고에만, 연결부는 참조만 받음. AI 대화·화면·공개 저장소에 비밀 값 없음. 고객 장비 기록은 공개 MCP 저장소 밖.

## 9. (부록 B) 첫 업무 상세 명세 — 백업 실패 슬라이스 (계약)
원칙: PRD를 더 두껍게 쓰지 않고, 이 한 흐름을 같은 정본에 계약으로 붙여 실제 코드로 돌린다. 기능 목록은 늘리지 않는다. 아래는 **모의 자료 기준**이며 실제 백업 제품의 성공 판정·이벤트 형식으로 가장하지 않는다.
- 뼈 = §2 D1–D12 / 근육 = 고객·장비·이벤트·사건·조치·검증 필드와 금지 전이 + 공통 수신 계약 / 살 = 화면 3개가 그 상태를 그대로 표시(화면만 먼저 만들지 않음)
- 공통 수신 계약: 고객+소스+원본 이벤트 ID로 중복 제거, *내구성 있게 접수된 뒤에만* 수신 성공 응답(수신 성공 = 접수 보장이지 사건 처리 완료가 아님). 접수 이벤트에 처리 상태·실패 사유 기록, 재시작 후 미처리 건 재처리 시 사건 중복 없음. 시험 중 입력은 가짜 소스.
- 실제 소스(SCP·FortiManager·Zabbix 등)는 단순 교체가 아니다: 소스별 식별자·순서·재전송 특성을 *연결부에서 검증*해 공통 수신 계약을 충족해야 하며, 검증표(§8) 통과 후 연결.

## 부록 D. 고객·시장 가설 (2026-10-10 4자 합의, 결론 미잠금)
확인된 사실: '통합관리 솔루션'은 우리가 제안한 해결책이다. 고객이 그것을 필요로 한다는 근거는 아직 없다. (고객이 제품 이름을 먼저 말해야만 수요인 것은 아니며, 반복 장애·대응 지연·실제 지출도 근거가 될 수 있다.)
두 가설을 분리해 유지: **H1 고객 수요**(업무가 멈추지 않음·빨리 앎·해결할 사람·감사 증빙) / **H2 BLRO 내부 효율화**(BLRO가 구매자인 운영비 절감). H2를 고객 요청으로 바꾸지 않는다.
고객 대응 과정(PRD 앞단, 나희): 누가 발견하나(직원 신고·장비 경보·외부 관제) → 누가 판단하나(고객 IT·BLRO·보안 전문업체, 부재 시 대체자) → 누가 조치하나(원격·현장) → 누가 복구를 확인하나. 책임은 계약과 실제 역량으로 정한다. 비전문가에게 제조사 콘솔의 기술 조작을 떠넘기지 않되, 고객의 영향 설명·조치 승인·업무 복구 확인 역할은 남는다.
지연 원인 구분: 도구 부족 / 권한·계약·인력 문제. 후자라면 통합 화면만으로 해결되지 않는다.
사례 표 칸: 고객 발언 / 관찰된 사건·행동 / 우리 해석 / 구매 근거 (발견→첫 연락→조치→복구 확인별 담당·근거).
근거 순서: ① 재민의 최근 장애 사례 1건(실명·접속정보 불필요, 승인 불필요) ② BLRO 장애 접수 기록(승인 필요) ③ 고객 3곳 질문(문안 승인 필요). 감으로 받은 비율은 탐색 참고만, 실측으로 기록 금지. 사례 1건은 시장 전체 수요·구매 의사를 입증하지 않는다.
시장 조사 범위(잠금): 문제 3개(백업 확인·통신 책임 구간·변경 후 검증) × 기존 대안 × 가격·도입 난도 × 충족 여부·공백 가설 × 판정(유료 서비스 기회 / 반복 공백의 제한적 개발 / 사업·개발 보류). 공개 자료는 지금 가능, 내부 기록·외부 접촉은 승인 필요. 상포는 배제도 확정도 아님. 담당: 나희 초안, 가재 반론 검수, 서윤 D11·격리 관점, 오모 반영.
